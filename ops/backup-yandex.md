# Резервные копии в Yandex Object Storage (STANDARD, российский регион)

Дополнение к `backup.md`. Ничего из этого не выполнялось: аккаунта, ключей и бакета нет, секреты я не создавал и не видел.

## 1. Почему этот вариант
- Данные в России (регион `ru-central1`, Россия) — требование локализации ПДн (ст. 18 ч. 5 152-ФЗ, см. `legal/pd-audit.md`); в бакете лежат только зашифрованные `age` файлы, ключа у провайдера нет.
- S3-совместимый протокол, поддерживается `rclone`. Класс STANDARD — без минимального срока хранения и без платы за извлечение, подходит для копий, которые читаются редко.
- Договор с Yandex Cloud нужен в любом случае; провайдер юридически — место хранения ПДн (учесть в реестре обработчиков).

## 2. Объём и стоимость (оценка)
Расчёт — `node ops/backup-sizing.mjs` (синтетическая база той же схемы; параметры меняются: `--carts-per-day`, `--quotes-per-day`, `--price`). **Реальной базы у меня нет**, поэтому цифры — для сценариев; реальный размер `cart.sqlite` и число заявок даст `ops/vps/preflight.sh --db`.

Средний сценарий (150 корзин и 8 заявок в день): база растёт ≈ 110 КБ в сутки (≈ 40 МБ в год), копия после сжатия и шифрования ≈ 26% размера базы. При ротации 14 суточных + 8 недельных + 12 месячных в хранилище одновременно до 34 копий:

| Через | База | Одна копия | Всего в бакете | ₽/мес (2,01 ₽/ГБ после бесплатного 1 ГБ) |
|---|---|---|---|---|
| 0,5 года | 20 МБ | 5 МБ | 174 МБ | 0 ₽ |
| 1 год | 39 МБ | 10 МБ | 348 МБ | 0 ₽ |
| 3 года | 118 МБ | 31 МБ | 1,0 ГБ | ≈ 0,04 ₽ |
| 3 года, «много» (1000 корзин, 40 заявок в день) | — | 200 МБ | 6,6 ГБ | ≈ 11 ₽ |

Операций (запись, перечень, удаление) — порядка 190 в месяц: на цене они не сказываются. **Итог: практически бесплатно**, пока база меньше ~100 МБ.

Тариф: по правилам тарификации Yandex Cloud первый 1 ГБ хранения STANDARD в месяц не тарифицируется; в примерах документации цена 1 ГБ — около 2,01 ₽/мес, запись — порядка 1,39 ₽ за 1000 операций. **Эти цифры я не смог открыть на самом сайте из своей среды (доступ к yandex.cloud закрыт), поэтому считайте их ориентировочными и сверьте с прайсом и калькулятором перед созданием бакета** (регионы Россия и Казахстан тарифицируются по-разному; цены с НДС или без — проверьте).

Корзины в базе сами не удаляются, поэтому база растёт линейно. Если хотите сократить, позже можно добавить чистку старых пустых корзин (отдельная задача, существующие данные я не трогал).

Локально на VPS хранятся только последние 7 копий (`LOCAL_KEEP_DAILY`), остальная история — в бакете.

## 3. Что создать в консоли Yandex Cloud (вручную, вы)
1. Отдельный **каталог** (folder) только для копий — например `italon-backups`, чтобы права сервисного аккаунта не касались других ресурсов.
2. **Бакет** в этом каталоге: имя уникальное (например `italon-x2-backups-<случайные 6 символов>`), класс хранилища **STANDARD**, доступ **закрыт** (чтение, список и конфигурации — «Ограничен»), шифрование на стороне сервера — по желанию (клиентское `age` уже есть).
3. **Сервисный аккаунт** `italon-backup` с ролью `storage.editor` только на этот каталог (редактор нужен: скрипт загружает копии, проверяет размер и удаляет устаревшие; роль `storage.uploader` не подходит — не умеет удалять и читать список).
4. **Статический ключ доступа** сервисного аккаунта: идентификатор и секрет показываются один раз — сохраните в менеджере паролей. Не отправляйте их в чат, в GitHub и не вставляйте в команды.
5. Необязательно: правило жизненного цикла «удалять незавершённые multipart-загрузки через 1 день»; **бюджет с уведомлением** на небольшую сумму (например 100 ₽/мес) в разделе «Биллинг».
6. Версионирование и блокировки объектов можно включить для защиты от удаления с взломанного сервера, но они увеличивают объём (хранятся удалённые версии) и конфликтуют с ротацией — по умолчанию не включайте, пока не решите, что нужно.

## 4. Настройка `rclone` на сервере (позже, с вашего разрешения)
Секреты не попадают в историю команд и в список процессов: вводятся скрытым вводом и записываются в файл с правами 600.

```bash
sudo -i
install -d -m 700 /root/.config/rclone
read -rsp 'Идентификатор ключа: ' KID; echo
read -rsp 'Секретный ключ: ' KSEC; echo
umask 077
cat > /root/.config/rclone/rclone.conf <<CONF
[italon-ru]
type = s3
provider = Other
access_key_id = ${KID}
secret_access_key = ${KSEC}
endpoint = https://storage.yandexcloud.net
region = ru-central1
acl = private
no_check_bucket = true
CONF
unset KID KSEC
chmod 600 /root/.config/rclone/rclone.conf
rclone lsf italon-ru:ИМЯ-БАКЕТА        # проверка доступа (список пуст — это нормально)
```
В `/etc/italon-backup.env`: `RCLONE_REMOTE=italon-ru:ИМЯ-БАКЕТА/prod` и `REQUIRE_OFFSITE=1`. Первый пробный запуск (`backup-run.sh`) создаст в бакете файлы `cart-<время>.sqlite.gz.age` и паспорт `.manifest.json`.

## 5. Ключ шифрования `age` (на вашем компьютере, не на сервере и не в чате)
```bash
age-keygen -o italon-backup.key           # закрытый ключ остаётся у вас; файл со строкой «# public key: age1…»
age-keygen -y italon-backup.key           # печатает только публичный ключ
```
- Публичную строку `age1…` запишите на сервере в `/etc/italon-backup/recipients.txt`. **Закрытый файл `italon-backup.key` никуда не отправляйте.**
- Храните закрытый ключ минимум в двух местах вне сервера (менеджер паролей с вложением + зашифрованная флешка/бумажная копия в сейфе). Потеря ключа = копии не прочитать.
- Рекомендуется **второй, запасной ключ** (другой `age-keygen`, хранится отдельно): добавьте его публичную строку второй строкой в `recipients.txt` — каждая копия расшифровывается любым из двух.
- При смене ключа новые копии шифруются новым; старые читаются старым ключом — храните оба.
- Проверка: `bash hosting/backup/restore-test.sh <файл>.age italon-backup.key` на своём компьютере (`backup.md` §4) — до включения расписания.

## 6. Проверка перед включением
Пробный запуск → файл виден в бакете → скачан на ваш компьютер → `restore-test.sh` сообщил `OK` и совпали число заявок и контрольная сумма → только затем `install.sh --enable`. Имитация сбоя (неверный ключ rclone) должна давать сообщение в Telegram — проверьте один раз.
