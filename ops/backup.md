# Резервные копии заявок

Заявки и корзины лежат в одной базе SQLite (`/data/cart.sqlite` в томе `cart_data` на сервере). Раньше резервной копии не было: потеря диска VPS = потеря всех заявок.

## 1. Что делает копирование (`hosting/backup/`)

Раз в сутки (03:20 по Москве, плюс страховочный запуск в 09:10, если ночью не получилось):

1. **Снимок базы штатным механизмом SQLite** (`backup()` из `node:sqlite` внутри контейнера приложения). Рабочий файл не копируется «на ходу» и не блокируется — приём заявок идёт параллельно (проверено тестом с одновременной записью).
2. **Проверка снимка** (`backup-verify.mjs`): `PRAGMA integrity_check`, число заявок и корзин, контрольная сумма, пробное открытие приложением на временной копии (миграции).
3. Сжатие и **шифрование `age`** открытым ключом. Закрытый ключ на сервере не хранится: украденная копия с сервера или из хранилища нечитаема.
4. Рядом кладётся «паспорт» копии (`*.manifest.json`: время, размер, sha256, числа записей) — **без персональных данных**.
5. Копия сохраняется на сервере (`/var/backups/italon`, быстрый доступ) **и** отправляется через `rclone` во внешнее хранилище; размер в хранилище сверяется с локальным.
6. Ротация: 14 ежедневных, 8 еженедельных, 12 ежемесячных; не меньше 3 последних копий не удаляется никогда.
7. Ошибка на любом шаге → сообщение в Telegram (без персональных данных, только «что и на каком шаге»). Отдельный «сторож» раз в сутки проверяет, что последняя удачная копия не старше 30 часов, и сообщает, если копирование вообще не запускалось (сломался таймер/сервер). Необязательно: «пульс» во внешний монитор (healthchecks.io) — получает пустой запрос.

Существующие заявки скрипт **только читает**, не изменяет и не удаляет.

## 2. Требования 152-ФЗ к месту хранения копий

- Копии содержат персональные данные граждан РФ (ФИО, телефон, адрес). По ст. 18 ч. 5 152-ФЗ запись, систематизация, хранение и извлечение ПДн граждан РФ должны выполняться **с использованием баз данных на территории РФ** — это относится и к резервным копиям.
- Поэтому хранилище для `RCLONE_REMOTE` выбирается **российское**: Яндекс Object Storage, Selectel, VK Cloud, Cloud.ru или Яндекс Диск (все работают через `rclone`, S3-совместимые). Зарубежные (Backblaze, AWS, Google Drive, Dropbox) **не использовать**.
- С выбранным провайдером нужен договор; он обрабатывает только зашифрованные данные и ключа не имеет, но юридически всё равно фиксируется как место хранения (§ в `legal/pd-audit.md`).
- Шифрование — дополнительная мера защиты (ст. 19), а не замена требованиям о локализации.
- `REQUIRE_OFFSITE=1` (по умолчанию): без внешнего хранилища копирование считается неудачным и присылает сообщение, чтобы никто не думал, что копии «где-то есть».
- Какое именно хранилище выбрать — решение владельца (нужна учётная запись и оплата, поэтому я их не создавал).

## 3. Установка (человеком, на сервере; сайт не затрагивается)

```bash
git clone --depth 1 -b stage1/safe-release https://github.com/ronineditingwork-bro/italon-x2 /tmp/italon && cd /tmp/italon
sudo bash hosting/backup/install.sh          # ставит файлы и пакеты age/rclone; таймеры НЕ включает
```

1. **Ключ шифрования — на своём компьютере**, не на сервере: `age-keygen -o italon-backup.key`. Строку `Public key: age1…` записать на сервере в `/etc/italon-backup/recipients.txt`. Файл `italon-backup.key` сохранить минимум в двух местах вне сервера (менеджер паролей, флешка в сейфе). **Потеря ключа = копии невозможно прочитать.**
2. `rclone config` — создать хранилище в РФ; имя вписать в `RCLONE_REMOTE` в `/etc/italon-backup.env`. Учётные данные rclone лежат в `/root/.config/rclone/` (доступ root). Хорошо: отдельный сервисный ключ с правом только записи/чтения в одном бакете.
3. Пробный запуск: `sudo /usr/local/lib/italon-backup/backup-run.sh` — только читает рабочую базу, создаёт копию, шлёт «✅» в Telegram.
4. **Проверка восстановления (обязательна до включения расписания)** — §4.
5. `sudo bash hosting/backup/install.sh --enable` — включает таймеры.

## 4. Проверка восстановления (на тестовой копии)

Не трогает рабочую базу и не заменяет её. Удобнее делать на своём компьютере (нужны `age`, Node.js 22+):

```bash
rclone copy italon-ru:italon-backups/<файл>.sqlite.gz.age .      # + рядом *.manifest.json
bash hosting/backup/restore-test.sh <файл>.sqlite.gz.age italon-backup.key
```

Скрипт расшифровывает во временный каталог, распаковывает, проверяет целостность, открывает базу кодом приложения (миграции на копии), сверяет с паспортом (sha256, число заявок/корзин) и удаляет временные файлы. `OK` в конце = копия пригодна. Повторять **раз в квартал** и после смены хранилища/ключа.

Эта проверка в моей среде прогнана на синтетической базе (6 тестов `tests/backup.test.mjs`: успех, запись во время копирования, сбои с уведомлениями, порча файла, ротация, сторож). С настоящим `rclone`-хранилищем, systemd и реальной базой — **не проверялась**, нужен сервер.

## 5. Восстановление боевой базы (авария)

Только при реальной потере/порче базы; делается человеком.

1. `touch /opt/italon-x2/.freeze` (остановить автовыкладки).
2. Скачать нужную копию, расшифровать и проверить на отдельной машине (§4) — убедиться, что это то, что нужно.
3. Остановить только приложение: `docker compose -f /opt/italon-x2/compose.yaml stop app` (Caddy продолжит отдавать 502 — приём заявок на это время недоступен).
4. **Сохранить текущий файл**, даже повреждённый: `docker run --rm -v italon-x2_cart_data:/d -v /root:/o alpine cp -a /d/cart.sqlite /o/cart.sqlite.broken-$(date +%F)` (имя тома уточнить `docker volume ls`).
5. Положить восстановленный `cart.sqlite` в том, удалить рядом `cart.sqlite-wal` и `-shm`, права как у прежнего файла.
6. `docker compose … start app`, проверить `/healthz`, `italon-rollback --list`, заявку из админского Telegram-чата.
7. Снять `.freeze`.

## 6. Ограничения и риски

- Периодичность суточная: при аварии можно потерять заявки за последние до 24 часов. Telegram-сообщения менеджеру при этом остаются в чате — это вторая копия заявки. Если нужна меньшая потеря — запускать чаще (таймер) или Litestream (отложено).
- Если сервер потерян полностью, а ключ у владельца есть — база поднимается из хранилища на новом VPS за ~15 минут.
- `rclone`-токен Яндекс Диска периодически протухает — для него лучше S3-ключи (Object Storage). Сторож заметит, если копии перестали доезжать.
- Docker-журналы приложения могут содержать IP и номера в ошибках — см. `legal/pd-audit.md` (ротация журналов).
