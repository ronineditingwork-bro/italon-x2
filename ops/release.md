# Безопасная выкладка и откат

## 1. Как работает сейчас (и в чём риск)

- На сервере (Reg.ru VPS, Docker + Caddy) таймер `italon-autoupdate` раз в 5 минут смотрит ветку **`ccr-943f3ebb-rcco8n`** и при любом новом коммите запускает `hosting/deploy-reg-ru.sh`, который берёт этот же скрипт из той же ветки.
- Значит, **любой коммит в эту ветку попадает на боевой сайт без проверок**; сборка идёт на сервере; каталог выкладки переписывается `rsync --delete`, затем `docker compose up -d --build` пересоздаёт контейнер. Если версия собралась, но не работает, сайт остаётся сломанным до следующего коммита; откат — пересборка старого коммита (минуты).
- Настройки автообновления (`REPO`, `BRANCH`) лежат на сервере в `/etc/italon-autoupdate.env`. Другие ветки сервер не читает, но изменения `hosting/deploy-reg-ru.sh` и `hosting/auto-update.sh` в боевой ветке начинают действовать сразу — поэтому эти два файла в этапе 1 не менялись (контроль: `ops/legacy-deploy.sha256`, тест `ci-config`).

## 2. Как будет работать (механизм «только проверенные версии»)

```
разработка ─▶ ветка ─▶ (PR) ─▶ main ──push──▶ GitHub Actions: CI (3 задания)
                                  │                       │ результат виден в публичном API GitHub
                                  ▼                       ▼
                  сервер, раз в 5 мин: берёт верхушку main и ВЫКЛАДЫВАЕТ, только если
                  verify-ci.py подтвердил: коммит в истории main И все 3 задания CI успешны (создатель — приложение github-actions)
```

**Почему именно так.** Репозиторий публичный и принадлежит *личному* аккаунту. У таких репозиториев нельзя написать правило «в ветку `release` пушит только GitHub Actions»: список «кому разрешена запись» и исключения для приложений доступны только организациям, а владелец-администратор обходит правила или вынужден отключать их у себя. Поэтому доверие проверяет **сам сервер** — на каждом коммите, перед сборкой. Это не зависит от настроек GitHub, которые нельзя гарантировать.

1. **CI** (`.github/workflows/ci.yml`) на каждый коммит и запрос на слияние: синтаксис, модульные тесты, тесты скриптов выкладки/копий/согласия, полная сборка сервера, **сборка сайта и проверка каталога** (`scripts/verify-catalog.mjs`: 1202 позиции и 75 коллекций, страницы, фото, цены, ~83 тыс. ссылок, sitemap, бюджеты размера), интерфейс корзины, игра, **браузерные сценарии на настоящем сервере** и **сборка образа Docker с запуском и проверкой**. У CI только чтение кода, секретов и доступа к серверу нет (тест `ci-config`).
2. **Сервер** (`hosting/release/auto-update.sh`, раз в 5 минут) смотрит верхушку `main`. Новый коммит принимается, только если `verify-ci.py` (публичный API GitHub, токен не нужен) подтвердил:
   - коммит входит в историю `main`;
   - три обязательных задания CI завершились успешно **именно на этом коммите** (последний запуск; перезапущенный и ставший зелёным засчитывается);
   - проверки созданы приложением `github-actions` (проверку от чужого приложения или «статус от руки» сервер не засчитывает).
   Проверки идут → ждёт (без тревоги). GitHub недоступен/лимит API → ждёт. Проверки провалены или коммит не из `main` → не выкладывает и один раз присылает сообщение.
3. Скрипты выкладки берутся из `/usr/local/lib/italon-release` (ставятся вручную `install.sh`), а **не** из скачанного коммита: изменить логику выкладки новым коммитом нельзя (в отличие от прежнего механизма).
4. **Выкладка без остановки** (`deploy-release.sh`):
   1. сборка версии в отдельном каталоге и образа `italon-x2-app:<sha12>` — **рабочий сайт не затронут**;
   2. снимок боевой базы штатным механизмом SQLite и запуск **кандидата на копии базы** (миграции проверяются на реальных данных);
   3. `smoke.mjs`: `/healthz`, главная и разделы, три страницы товаров и фото, `/api/catalog`, `catalog.json`, sitemap, 404, защита по Host, число позиций **не меньше, чем на рабочем сайте**;
   4. резервная копия перед переключением (если установлена);
   5. **заменяется только контейнер `app`** (`up -d --no-deps app`); Caddy, тома с заявками и сертификатами не трогаются; перерыв несколько секунд;
   6. проверка рабочего сайта; при сбое — **автоматический возврат предыдущего образа** и сообщение;
   7. запись версии (`.deployed-tag`, `.previous-tag`, `releases.log`); хранится 5 последних образов.
5. Не прошедшая проверку версия помечается `.attempted-commit` и не пересобирается в цикле. Пауза: `touch /opt/italon-x2/.freeze`.

Ветка `release` и workflow `promote-release.yml` — необязательный запасной путь (выключен, нужен `RELEASE_PROMOTION=true`). **Не используйте его вместе с защитой `release`** — см. §6.

## 3. Откат

| Ситуация | Что делать | Время |
|---|---|---|
| Новая версия не прошла проверку после переключения | Ничего: автооткат вернёт прежний образ и пришлёт сообщение | секунды |
| Версия «прошла», но заметили ошибку | `italon-rollback` (предыдущая) или `italon-rollback <тег>`; `--list` — список; `--freeze` — после отката остановить автовыкладку | ~10 с |
| Остановить любые выкладки | `touch /opt/italon-x2/.freeze` (снять: `rm …/.freeze`) | сразу |
| **Вернуться к версии «до перехода»** | `italon-rollback before-release` (§8, образ с этим тегом создаётся при установке) | ~10 с |
| Вернуться на прежний механизм (старое автообновление) | §9 | минуты |
| Повреждена база (не связано с версией сайта) | Восстановление из копии — `backup.md`, §5 | минуты |

Откат образа безопасен для данных: меняется только код, заявки лежат в томе `cart_data`. Миграции разрешены только добавляющие (тест `ci-config` запрещает `DROP/RENAME/DELETE/UPDATE`), поэтому прежний код работает на новой базе.

## 4. Что проверено

- **Настоящий Docker (репетиция в песочнице, не на VPS):** «старый» сайт поднят прежним способом (`docker compose up -d --build`, образ `italon-x2-app:latest`, база с тестовой заявкой), затем по очереди: тег `before-release` → `deploy-release.sh --dry-run` (кандидат на копии боевой базы, 1202 позиции, сайт не менялся) → настоящая выкладка (заменён только `app`, `caddy` продолжал работать, предыдущий тег записан) → `rollback.sh --freeze` на `before-release` (образ как до перехода, `read_only` и `cap_drop` сохранены, заявка в базе на месте, `.freeze` создан). Затем сквозной прогон: `auto-update.sh` взял верхушку ветки с настоящего GitHub, `verify-ci.py` подтвердил три проверки Actions, коммит собран и выложен (1202 позиции); коммит, не входящий в `main`, отклонён с сообщением; **автооткат после переключения** (имитация сбоя проверки) вернул предыдущий образ, `caddy` не перезапускался. Репетиция нашла и позволила исправить ошибки первой установки (§7).
- Заглушки docker/git (`tests/release-scripts.test.mjs`, 11 сценариев): dry-run, успех, провал кандидата/сборки/образа, провал после переключения → автооткат, freeze, автообновление (ожидание/отказ/один раз сообщение/выкладка), откат.
- `verify-ci.py` на заглушке API GitHub (`tests/verify-ci.test.mjs`, 7 сценариев) и **на настоящем GitHub** (коммит `cfc46e0e` — все три проверки найдены, чужие и неполные отвергаются).
- **Не проверено:** VPS Reg.ru (память 1 ГБ, диск, сеть), Caddy с настоящим сертификатом, `rclone` и systemd

## 5. Настройки GitHub

Репозиторий публичный, владелец — личный аккаунт. Сейчас: правил (rulesets) нет, ветки `main` и `ccr-943f3ebb-rcco8n` не защищены (проверено по публичному API). Рекомендуется (Settings → Rules → Rulesets, всё доступно бесплатно для публичных репозиториев):

1. Для `main`: **запретить force-push и удаление ветки** (не мешает обычной работе, в том числе загрузке файлов через веб-интерфейс).
2. Включить двухфакторную аутентификацию владельца и ключи доступа только у владельца: именно запись в `main` — граница доверия.
3. Необязательно, строже: требовать запрос на слияние и успешные проверки CI для `main`. Тогда загрузка файлов «Add files via upload» прямо в `main` станет невозможна (нужна ветка + PR). Сервер и без этого не выложит красный коммит.
4. Settings → Actions → General → Workflow permissions: оставить **Read repository contents** (по умолчанию). CI ничего больше не требует.
5. Не создавайте токены/секреты для сервера: сервер читает публичный репозиторий и публичный API без токена.

## 6. Совместимость Actions и защиты `release` (почему путь через `release` не выбран)

- `promote-release.yml` пушит в `release` токеном `GITHUB_TOKEN` с `contents: write`. Это разрешено явным `permissions:` в файле даже при ограничении «только чтение по умолчанию» — **пока на `release` нет защиты**.
- Если включить защиту `release` (require PR / required checks / restrict updates), этот пуш будет отклонён: у личного репозитория в список исключений нельзя добавить приложение GitHub Actions (только роли репозитория, т. е. самого владельца). Получается: либо защита, либо автоматический перенос, но не оба.
- Без защиты `release` в неё может записать сам владелец, что ничем не лучше `main`. Поэтому преимуществ у `release` нет, а лишняя ветка и лишние права записи для Actions есть. Выбран путь «сервер проверяет сам» (§2).
- Если когда-нибудь репозиторий перенесут в организацию (бесплатно), можно добавить ветку `release` с ограничением записи только для Actions; сервер тогда достаточно переключить на `BRANCH=release` — `verify-ci.py` продолжит работать.

## 7. Что нашла репетиция на настоящем Docker (исправлено в этой ветке)

1. До первой выкладки `compose.release.yaml` на сервере нет, а скрипты вызывали `docker compose` с ним — проверка «позиций на рабочем сайте» молча давала 0, и кандидат запускался на **пустой** базе вместо копии боевой. Теперь файл подключается, только если лежит рядом. Заглушки этого не видели.
2. Скрипт резервной копии вызывал `server/backup-verify.mjs` внутри контейнера, а в образе до перехода его нет → копия до первой выкладки не прошла бы. Теперь проверка подаётся с сервера через stdin и работает со старым образом.
3. Снимок исходников (~165 МБ, теперь с прайсами и архивами фото из `main`) копировался в каждый релиз; теперь удаляется после сборки образа. Первый клон делается без истории.

## 8. План первой установки на Reg.ru VPS (1 ГБ памяти)

Делается человеком, в спокойное время, заранее; **пока не выполняйте — нужно ваше разрешение на каждый шаг, затрагивающий VPS.** Сайт работает на прежнем механизме всё время до шага 8.

**Подготовка (ничего не меняет в работе сайта):**
0. Условия: свободно ≥ 4 ГБ диска (скрипт выкладки откажется работать при < 3 ГБ), есть `docker compose`, `git`, `curl`, `python3`. Память: измерено локально — сборка сайта пиково ≈ 180 МБ, образ Docker ≈ 430 МБ на диске (общий слой Node + ≈ 75 МБ на версию), контейнер приложения < 100 МБ; сборка идёт с `--max-old-space-size=512`. **Swap 2 ГБ уже создаёт прежний установочный скрипт** (`deploy-reg-ru.sh`, шаг 1/6) — это надо подтвердить (`ops/vps/preflight.sh` покажет); если swap нет, создайте его до установки, иначе на 1 ГБ ядро может убить сборку (OOM). При OOM кандидат не запускается, а рабочий сайт не затрагивается.
1. Снимок VPS у Reg.ru (панель) — резервная точка «до всего».
2. Проверить фактическое состояние **командами только для чтения**: `sudo bash ops/vps/preflight.sh --db > preflight.txt` (описание — `ops/vps/README.md`; скрипт ничего не меняет и не печатает секреты). Устранить все строки `[ПРОБЛЕМА]`.
3. `git clone --depth 1 -b <ветка после слияния в main> …` в `/tmp`, затем `sudo bash hosting/release/install.sh` — **только копирует файлы** (`/usr/local/lib/italon-release`, `italon-rollback`, `italon-compose`, `compose.release.yaml` в `/opt/italon-x2`), ничего не включает. Прежний таймер продолжает работать.
4. Резервные копии (`backup.md`): установка, ключ `age` на вашем компьютере, хранилище в РФ, пробный запуск, **проверка восстановления**, затем `--enable`.
5. **Метка версии «до перехода»:** `cd /opt/italon-x2 && docker tag $(docker compose images -q app) italon-x2-app:before-release && echo before-release > .deployed-tag`. Это единственная нужная команда для отката на то, что работает сейчас.
6. Пробный прогон: `/usr/local/lib/italon-release/deploy-release.sh $(git ls-remote https://github.com/ronineditingwork-bro/italon-x2 refs/heads/main | cut -f1) --dry-run`. Собирает образ и проверяет кандидата на копии базы; сайт не меняется (на 1 ГБ это самый тяжёлый момент — смотреть `free -m`, `dmesg | grep -i oom`). Исправлять, пока не пройдёт.
7. Остановить сторонние нагрузки на время первой выкладки (если есть).

**Переключение (первая настоящая выкладка):**
8. `systemctl disable --now italon-autoupdate.timer` (чтобы два механизма не работали одновременно; текущая версия остаётся работать), затем вручную: `/usr/local/lib/italon-release/deploy-release.sh <sha main>` с открытым `tail -f`; перерыв — секунды. Проверить сайт, форму заявки (тестовая, потом удалить/пометить), `italon-rollback --list`.
9. Если что-то не так — `italon-rollback before-release` (§3). Сайт вернётся на образ, собранный старым способом, заявки на месте.
10. Если всё хорошо: `systemctl enable --now italon-release-update.timer` (настройки нового механизма — в `/etc/italon-release.env`, по умолчанию `BRANCH=main`; **`/etc/italon-autoupdate.env` прежнего механизма не меняется**). Наблюдать неделю: `tail -f /var/log/italon-release.log`, сообщения в Telegram.

**Чего не делать:** не запускать одновременно прежнее и новое автообновление; не удалять `/opt/italon-x2/.env`, тома `cart_data`/`caddy_data`; не включать `RELEASE_PROMOTION`.

## 9. Откат на прежний механизм (полностью)

1. `systemctl disable --now italon-release-update.timer`
2. `systemctl enable --now italon-autoupdate.timer` (или `/usr/local/bin/italon-autoupdate`): прежний скрипт сам пересоберёт сайт `docker compose up -d --build`. Его настройки (`/etc/italon-autoupdate.env`, ветка `ccr-943f3ebb-rcco8n`) мы не меняли, править ничего не нужно.
3. Побочный эффект: его `rsync --delete` удалит служебные файлы нового механизма в `/opt/italon-x2` (`.deployed-tag`, `compose.release.yaml` …); образы Docker и база остаются. Перед повторным переходом выполните §8, шаги 3 и 5 заново.

## 10. Риски и ограничения

- Один сервер: сборка идёт на VPS и занимает память/диск (§8). Улучшение на будущее: сборка образа в GitHub и загрузка в реестр.
- Перерыв при смене контейнера — секунды. Полностью без перерыва нужны две реплики.
- Доверие держится на аккаунте владельца GitHub (запись в `main`) и на самом GitHub (результаты Actions). Сервер не защитит от захвата аккаунта владельца: включите 2FA.
- Закреплять `actions/checkout`/`setup-node` по SHA и включить Dependabot — желательно, пока не сделано.
- Публичный API GitHub: лимит 60 запросов/час на IP; вызывается только при появлении нового коммита, этого достаточно.

## 11. Совместимость новой установки с действующим автообновлением

Проверено чтением скриптов и тестом `tests/install-compat.test.mjs` (6 проверок).

| Что | Прежний механизм | Новый механизм | Вывод |
|---|---|---|---|
| Службы systemd | `italon-autoupdate.{service,timer}` | `italon-release-update.*`, `italon-backup*` | имена разные; установка **ничего не включает** |
| Команды | `/usr/local/bin/italon-autoupdate` | `italon-rollback`, `italon-compose` | не пересекаются |
| Настройки | `/etc/italon-autoupdate.env` (REPO, BRANCH) | `/etc/italon-release.env` (необязательный) | новый **не читает и не меняет** файл прежнего (исправлено: раньше читал) |
| Журналы | `/var/log/italon-autoupdate.log` | `/var/log/italon-release.log` | разные |
| Замок | `/var/lock/italon-autoupdate.lock` | тот же файл | **общий** (исправлено: был отдельный): два механизма не могут выкладывать одновременно |
| Каталог сборки | `/opt/italon-x2-src` (shallow clone ветки) | тот же каталог (fetch по sha, `checkout -f`) | совместимо под общим замком; клон без полной истории |
| Каталог сайта `/opt/italon-x2` | `rsync -a --delete`, исключения: `.env`, `.deployed-commit`, `.attempted-commit` | добавляет `compose.release.yaml`, `.deployed-tag`, `.previous-tag`, `.freeze`, `.rejected-commit`, `releases.log` | пока работает только прежний механизм, новые файлы он **удалит** при своей выкладке — это безопасно до переключения; `.env` и база не затрагиваются |
| Образы Docker | `italon-x2-app:latest` (тег переписывается при его сборке) | `italon-x2-app:<sha12>` и `before-release` | теги разные; очистка образов нового механизма трогает только `sha12` |
| Состояние | `.deployed-commit` (sha ветки) | то же имя, тот же смысл | совместимо |
| swap | создаёт 2 ГБ, если swap нет | ничего не создаёт | прежний уже подготовил |

**Предупреждения.**
1. Повторный запуск прежнего установщика (`curl …/deploy-reg-ru.sh | bash` из его же инструкции) **заново включит прежний таймер** и пересоберёт сайт старым способом. После переключения на новый механизм так не делайте; если сделали — выключите `italon-autoupdate.timer` снова.
2. Между установкой скриптов (§8, шаг 3) и переключением (шаг 8) прежнее автообновление продолжает работать и при своей выкладке сотрёт `compose.release.yaml` из `/opt/italon-x2`; `install.sh` кладёт его заново. Поэтому шаги 3 → 6 → 8 делают подряд, без пауз в днях.
3. Пока работают оба таймера (этого быть не должно), выкладку выполнит тот, кто первым взял замок; второй тихо завершится.
