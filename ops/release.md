# Безопасная выкладка и откат

## 1. Как работает сейчас (и в чём риск)

- На сервере (Reg.ru VPS, Docker + Caddy) таймер `italon-autoupdate` раз в 5 минут смотрит ветку **`ccr-943f3ebb-rcco8n`** и при любом новом коммите запускает `hosting/deploy-reg-ru.sh`, который берёт этот же скрипт из той же ветки.
- Значит, **любой коммит в эту ветку попадает на боевой сайт без проверок**; сборка идёт на сервере на 1 ГБ памяти; каталог выкладки переписывается `rsync --delete`, затем `docker compose up -d --build` пересоздаёт контейнер. Если новая версия собралась, но не работает, сайт остаётся сломанным до следующего коммита.
- Откатываться приходилось бы пересборкой старого коммита (минуты).
- Настройки автообновления (`REPO`, `BRANCH`) лежат на сервере в `/etc/italon-autoupdate.env`. В репозитории по умолчанию стоит `main`, на сервере записано `ccr-943f3ebb-rcco8n`. **Любая другая ветка сервером не читается**, но любые изменения `hosting/deploy-reg-ru.sh` и `hosting/auto-update.sh` в боевой ветке начинают действовать сразу — поэтому они в этой работе не менялись (контроль: `ops/legacy-deploy.sha256`, тест `ci-config`).

## 2. Как будет работать (механизм «только проверенные версии»)

```
разработка ──push──▶ ветка stage1/…  ──PR──▶ main ──CI зелёный──▶ ветка release ──▶ сервер (раз в 5 мин)
                         │                    │                       ▲
                    CI проверяет        CI проверяет            только Actions
                    каждый коммит       ещё раз на main         (fast-forward)
```

1. **CI** (`.github/workflows/ci.yml`) на каждый коммит и запрос на слияние: синтаксис, модульные тесты (каталог, расчёт, заявки), тесты проверок и скриптов (резервные копии, выкладка, согласие), полная сборка сервера и тест с корзиной/перезапуском/копией базы, **сборка сайта + проверка целостности каталога** (`scripts/verify-catalog.mjs`: 1202 позиции и 75 коллекций на месте, у каждой позиции страница, фото и цена, нет битых ссылок среди ~83 тыс., sitemap совпадает со страницами, бюджеты размера), интерфейс корзины, игра, **браузерные сценарии на настоящем сервере** (каталог, карточка, калькулятор, форма КП, PDF, заявка) и **сборка образа Docker с запуском и проверкой**. CI только читает код: секретов и доступа к серверу у него нет (проверяет `tests/ci-config.test.mjs`).
2. **Promote release** (`.github/workflows/promote-release.yml`): после успешного CI на `main` переносит этот же коммит в ветку `release` (только «вперёд», без принудительной записи). **Выключен по умолчанию** — работает, только если в репозитории задана переменная `RELEASE_PROMOTION=true`.
3. **Сервер** (после перехода) следит только за веткой `release` (`hosting/release/auto-update.sh`). В `release` коммиты попадают только от Actions (защита ветки — §6), поэтому сервер получает исключительно проверенные версии.
4. **Выкладка без остановки** (`hosting/release/deploy-release.sh`):
   1. собирает версию в отдельном каталоге и образ Docker `italon-x2-app:<sha12>` — **рабочий сайт не затронут**;
   2. делает снимок боевой базы штатным механизмом SQLite и запускает **кандидата на копии базы** (так миграции проверяются на реальных данных, а не на рабочей базе);
   3. прогоняет `smoke.mjs`: `/healthz`, главная и все разделы, три страницы товаров и их фото, `/api/catalog`, `catalog.json`, sitemap, 404, защита по Host, число позиций **не меньше, чем на рабочем сайте**;
   4. перед переключением делает резервную копию (если установлено резервное копирование);
   5. обновляет `compose.yaml`/Caddyfile, **заменяет только контейнер `app`** (`up -d --no-deps app`; Caddy, тома с заявками и сертификатами не трогаются — перерыв несколько секунд, а при `lb_try_duration` в Caddyfile посетители его не заметят);
   6. проверяет рабочий сайт ещё раз; **если что-то не так — автоматически возвращает предыдущий образ** и присылает сообщение;
   7. запоминает версию (`.deployed-tag`, `.previous-tag`, `releases.log`) и оставляет 5 последних образов.
5. Любая версия, не прошедшая проверку, помечается `.attempted-commit` и **не пересобирается в цикле** — ждёт нового коммита.
6. Пауза: `touch /opt/italon-x2/.freeze` — выкладки и автообновление ничего не делают, пока файл есть.

## 3. Откат

| Ситуация | Что делать | Время |
|---|---|---|
| Новая версия не прошла проверку | Ничего: автооткат сам вернёт прежний образ и пришлёт сообщение | секунды |
| Версия «прошла», но заметили ошибку | `italon-rollback` (вернёт предыдущую) или `italon-rollback <тег>`; список: `italon-rollback --list`. С `--freeze` автовыкладка остановится, пока вы не поправите | ~10 секунд |
| Нужно остановить любые выкладки | `touch /opt/italon-x2/.freeze` (снять: `rm …/.freeze`) | сразу |
| Вернуться на прежний механизм (старое автообновление) | `systemctl disable --now italon-release-update.timer && systemctl enable --now italon-autoupdate.timer`; в `/etc/italon-autoupdate.env` вернуть `BRANCH=ccr-943f3ebb-rcco8n` | минуты |
| База повреждена (редкий случай, не связан с версией сайта) | Восстановление из зашифрованной копии — `backup.md`, §5 | минуты |

Откат на прежний образ **безопасен для данных**: образ меняет только код, а заявки лежат в отдельном томе `cart_data`. Миграции базы разрешены только добавляющие (пустые столбцы/таблицы); тест `ci-config` запрещает `DROP/RENAME/DELETE/UPDATE`, поэтому старый код спокойно работает на новой базе.

## 4. Что проверено без сервера

- Заглушки docker/git (`tests/release-scripts.test.mjs`, 10 сценариев): dry-run ничего не переключает; успешная выкладка переключает **только после** проверки кандидата; провал кандидата, сборки, образа или недоступный docker — рабочий сайт не меняется; провал проверки или health после переключения — автооткат; freeze; автообновитель не видит чужих веток и не пробует неудачную версию дважды; откат помнит порядок, не откатывает на отсутствующий образ.
- `smoke.mjs` прогнан на настоящем сервере из сборки (тест `hosting.test.mjs`), в том числе проверка «потерянных позиций».
- **Не проверено (нужен сервер/GitHub):** реальное поведение Docker (сборка образа, `up --no-deps`), первый запуск workflow `image`, права записи Actions в ветку `release`. Поэтому первая выкладка делается вручную в режиме `--dry-run` и под наблюдением (§5).

## 5. Переход на новый механизм (без остановки сайта)

Делается один раз, человеком. Сайт всё это время работает на прежнем механизме.

1. **GitHub.** Просмотреть и принять ветку `stage1/safe-release` (запрос на слияние → `main`). `main` сейчас отстаёт от боевой ветки на 93 коммита, ветка `stage1/safe-release` построена от боевой, поэтому слияние в `main` — «вперёд» (без конфликтов).
2. Убедиться, что CI на `main` зелёный. Включить защиту веток (§6).
3. **Сервер, без переключения:** `bash hosting/release/install.sh` (только копирует файлы, ничего не запускает и не включает), затем:
   `/usr/local/lib/italon-release/deploy-release.sh <sha main> --dry-run`
   Он соберёт образ и проверит кандидата на копии боевой базы; сайт не меняется. Исправить, если упадёт.
4. Включить копии (`backup.md`) **до** первой настоящей выкладки.
5. В репозитории задать `RELEASE_PROMOTION=true` → ветка `release` появится сама после ближайшего зелёного `main`.
6. **Первая настоящая выкладка вручную**, в спокойное время, с открытым журналом:
   `systemctl stop italon-autoupdate.timer && /usr/local/lib/italon-release/deploy-release.sh <sha release>`
   Проверить сайт, `italon-rollback --list`. Если что-то не так — `italon-rollback` вернёт прежнюю версию (но образ «до перехода» собран старым способом, поэтому перед первой выкладкой тегируем его: `docker tag $(docker compose images -q app) italon-x2-app:before-release && echo before-release > /opt/italon-x2/.deployed-tag`).
7. В `/etc/italon-autoupdate.env` оставить `REPO`, поставить `BRANCH=release`; `systemctl enable --now italon-release-update.timer`; прежний таймер остаётся выключенным.
8. Следить неделю: `tail -f /var/log/italon-release.log`, сообщения в Telegram.

## 6. Настройки GitHub (делаются в интерфейсе, права владельца)

- **Settings → Branches → Add rule:** для `main` — требовать успешные проверки `CI` и запрещать принудительную запись; для `release` — «Restrict who can push» (только GitHub Actions / владелец) и запрет force-push и удаления. Тогда в `release` не попадёт ничего, кроме проверенного.
- **Settings → Secrets and variables → Actions → Variables:** `RELEASE_PROMOTION=true` (когда будете готовы).
- Прежняя боевая ветка `ccr-943f3ebb-rcco8n` после перехода не читается сервером; её можно оставить как архив.

## 7. Риски и ограничения

- Сервер всё ещё один (VPS 1 ГБ): сборка идёт на нём и временно занимает память/диск (нужно ≥ 3 ГБ свободно — проверяется). Это можно улучшить позже сборкой в GitHub и передачей готового образа.
- Перерыв при смене контейнера — секунды; полностью «ноль простоя» требует двух реплик (отложено).
- CI на GitHub-hosted runners использует минуты тарифа репозитория; полный прогон ≈ 6–10 минут.
- Версии сторонних Actions (`checkout`, `setup-node`, `upload-artifact`) закреплены по основной версии `@v4`; для строгой защиты цепочки поставки закрепите их по SHA (Dependabot).
