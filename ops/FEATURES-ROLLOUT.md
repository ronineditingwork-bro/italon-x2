## 2. Что можно сказать про совместимость заранее
Известно из кода каталога (не из самих функций):
- В каталоге 1202 позиции и 75 коллекций, у каждой позиции есть фото (WebP до 900 px) и цена; эталон и проверка — `ops/catalog-baseline.json`, `scripts/verify-catalog.mjs`. Любая функция подбора обязана ссылаться только на существующие артикулы (проверяемо тестом по `catalog.json`).
- Сборка сайта статическая; серверная часть — Node-приложение за Caddy (`hosting/server.mjs`, `worker/api.mjs`) с SQLite и лимитом частоты. Серверный подбор по описанию/картинке потребовал бы нового API и (если используется внешняя модель) исходящих запросов с сервера, который не достаёт до `api.telegram.org` — доступность внешних адресов нужно проверять `ops/vps/preflight.sh`.
- Новый механизм выкладки гарантирует: проверку каталога в CI, запуск кандидата на копии боевой базы, `smoke.mjs` до и после переключения, автооткат и откат на `before-release`. Новые функции пройдут через него без изменений, если не ломают существующие страницы и API.

## 4. Требования к функциям до внедрения (когда код найдётся)
Все пункты проверяются до слияния; ничего не выкладывается без выполнения.

**Общие**
1. Новая функция живёт за флагом: сборка `FEATURE_PICKER_TEXT=1` / `FEATURE_PICKER_IMAGE=1` (по умолчанию выключены); с выключенными флагами сайт **побайтно равен текущему** (как проверено для согласия на ПДн).
2. Не меняет существующие страницы, корзину, КП и API `/api/cart`, `/api/quote`; миграции базы только добавляющие.
3. Тесты в CI: правильные артикулы (все результаты есть в каталоге и имеют фото/цену), пустой/длинный/странный ввод, нагрузка/лимит частоты, отсутствие ошибок консоли, мобильная ширина, доступность (клавиатура, подписи), `verify-catalog` без ошибок.
4. Размер: бюджеты размера в `verify-catalog.mjs` не нарушены (новые файлы грузятся только после обращения к функции).
5. Не требуется новых секретов в репозитории; ключи — только в `.env` на сервере.

**По описанию (текст)**
- Если подбор локальный (по полям каталога: цвет, фактура, формат, коллекция) — внешних передач нет, это самый безопасный вариант и его можно публиковать первым.
- Если используется внешняя модель — это передача текста запроса третьей стороне (возможно за рубежом): отразить в политике и согласии, не отправлять ПДн, лимиты, таймауты, запасной вариант без модели при отказе, учёт стоимости.

**По картинке**
- Загруженное изображение может содержать людей/интерьер → считать потенциальными ПДн: не сохранять на сервере (обрабатывать в браузере или в памяти и сразу удалять), предупредить пользователя, не писать в журналы. Вариант «в браузере» (цвет/узор по пикселям, локальная модель) не передаёт ничего наружу.
- Лимиты: размер файла, тип (JPEG/PNG/WebP), частота запросов, защита от «бомб» декодирования; вынос тяжёлой работы из основного потока.
- Внешний сервис распознавания: те же условия, что выше, плюс отдельное согласие пользователя на передачу картинки.

## 5. Единый пошаговый план безопасного внедрения
Этапы идут строго по порядку; каждый следующий — только после зелёной проверки предыдущего и вашего решения. Сайт на всём пути работает на прежней версии, пока не выполнен шаг 8.

**0. Найти и собрать код** (блокер сейчас). Получить ветку/коммиты обеих функций; перенести в отдельную ветку `feature/picker` **от `stage1/integration`** (не от боевой). Ничего не публиковать.
**1. Проверка на соответствие §4.** Тесты и браузерные сценарии в CI; ревью безопасности (загрузка файлов, внешние вызовы), юридическая сверка (если внешняя модель/картинки).
**2. Слияние `stage1/integration` в `main`** вашим решением после просмотра (CI на `main` должен быть зелёным). Затем `feature/picker` → PR в `main` (флаги выключены), CI зелёный.
**3. Серверная подготовка по `CHECKLIST.md` B–C:** снимок VPS, `preflight.sh`, установка копий и проверка восстановления, установка скриптов выкладки, метка `before-release`, `--dry-run`.
**4. Первое переключение сайта на новую систему** (`CHECKLIST.md` D) — **без новых функций** (флаги выключены); неделя наблюдения. Так проверяется сама система, а функции не смешиваются с ней.
**5. Резервная копия перед включением функций:** `backup-run.sh` вручную, подтверждение в бакете, `restore-test.sh` OK, `releases.log` без сбоев.
**6. Выкладка функции с выключенным флагом:** обычная выкладка (`verify-ci` → кандидат на копии базы → переключение); сайт тот же, код функции на сервере лежит выключенным.
**7. Включение для себя:** флаг включается отдельной выкладкой/настройкой `.env` (для серверной части) — сначала только по закрытому адресу/параметру для проверки вами (тестовые описания и картинки, замеры времени, ошибок и стоимости).
**8. Включение для всех:** публичный флаг; наблюдение первые сутки (журнал, Telegram-сообщения, `healthz`, число ошибок); при сбое — выключить флаг.
**9. Откат** на любом шаге: (а) выключить флаг; (б) `italon-rollback` на предыдущую версию; (в) `italon-rollback before-release` — вернуть то, что было до перехода; (г) база — из копии (`backup.md` §5). Заявки и корзины (том `cart_data`) откат кода не затрагивает.
