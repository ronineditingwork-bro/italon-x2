## 2. Что остаётся

**Требует вас (доступы/решения):**
1. Выбрать российское хранилище копий и завести учётную запись; создать ключ `age-keygen` на своём компьютере и хранить его вне сервера (≥ 2 места).
2. Принять ветку в `main`, включить защиту веток `main`/`release`, затем `RELEASE_PROMOTION=true` (`release.md` §5–6).
3. Юрист: заполнить и утвердить политику и согласие, решить вариант A/B/C по Telegram, подать уведомления РКН (ст. 12 и ст. 22), оформить поручения (`pd-audit.md` §5–7).
4. Ответить на вопросы: правовая форма оператора; площадка VPS; Cloudflare проксирует домен или только DNS; есть ли запись в реестре РКН.

**Технически не проверено (нужна реальная среда):**
- настоящие сборка образа и `up -d --no-deps app` на сервере, поведение compose-override;
- `rclone` с реальным хранилищем, systemd-таймеры, уведомления в Telegram;
- ретранслятор Cloudflare с `RELAY_KEY`.

**Не реализовано сознательно:** админка заявок (вариант B), срок хранения/автоудаление, процедура ответа субъектам, сборка образа в GitHub вместо сервера, две реплики для нулевого простоя.

## 3. Найденные риски

1. Любой коммит в боевую ветку сразу попадает на сайт без проверок; выкладка тем же скриптом, что лежит в той же ветке (`rsync --delete`, пересборка на VPS 1 ГБ). Сломанная версия остаётся до следующего коммита.
2. **Резервных копий не было**: потеря диска VPS = потеря всех заявок.
3. Нет политики и согласия на обработку ПДн; ПДн уходят в Telegram (за рубежом), возможно через Cloudflare (ст. 12, 18, 9 152-ФЗ).
4. Docker-журналы без ротации; сроков хранения заявок нет.
5. Ретранслятор Telegram открыт для любого, кто знает адрес (исправляется ключом `RELAY_KEY`, код готов, не включён).
6. Побочный эффект старого автообновления: `rsync --delete` удалит новые служебные файлы (`.deployed-tag` и др.) при откате на прежний механизм — не критично, но учтено в `release.md`.
7. Новые механизмы сами не проверены на реальном сервере — поэтому первая выкладка предусмотрена вручную, с `--dry-run`.

## 4. Изменения, готовые к безопасному внедрению

Порядок (подробно — `release.md` §5, `backup.md` §3): CI зелёный на ветке → слияние в `main` → установка скриптов на сервер **без включения** → `deploy-release.sh --dry-run` → копии + проверка восстановления → первая ручная выкладка → переключение таймера на `release`. Юридические флаги включаются отдельно и только после юриста. Ничто из этого не включается само: выкладка новой ветки на сервер не происходит, пока вы не измените `BRANCH` в `/etc/italon-autoupdate.env` (или не включите новый таймер).

## 5. Как выполняется откат

- Автоматически: если новая версия не проходит проверку после переключения, возвращается предыдущий образ (секунды), приходит сообщение.
- Вручную: `italon-rollback` (или `italon-rollback <тег>`, `--list`, `--freeze`) — запуск уже собранного образа, без сборки, ~10 секунд; заявки не затрагиваются.
- Остановить выкладки: `touch /opt/italon-x2/.freeze`.
- Вернуться к прежнему механизму: выключить новый таймер, включить `italon-autoupdate.timer`, вернуть `BRANCH=ccr-943f3ebb-rcco8n`.
- Потеря/порча базы: восстановление из зашифрованной копии (`backup.md` §5).
- Для самого репозитория: ветка отдельная; если что-то не так, её достаточно не сливать — боевая ветка осталась прежней.
